## REFUTED

Прочитал оба файла: `r1/a1.md` и `r1/a2.md`.

- **«`Speaker Config Id: 1 → 0` немедленно восстанавливает калибровку» → нет.** `tasdevice_config_put()` только меняет `tas_priv->cur_conf`, аппаратных writes нет. Без промежуточной загрузки возвращаем тот же выбранный конфиг. Совет README в таком виде — наебалово. [Linux `tas2781_hda.c`](https://github.com/torvalds/linux/blob/master/sound/hda/codecs/side-codecs/tas2781_hda.c).
- **«Ноль PC10 исключает потерю PC10 как источник разницы мощности» → нет.** Один замер при открытом PCM ничего не говорит о закрытом baseline. Сам счётчик LPIT действительно читает FFH/MSR; моя промежуточная реплика, что это другой счётчик, была ошибочной. [Linux `acpi_lpit.c`, `lpit_read_residency_counter_us()`](https://github.com/torvalds/linux/blob/master/drivers/acpi/acpi_lpit.c).
- **«Отсутствие `Unneeded loading dsp conf` доказывает калибровку» → нет.** Это доказывает выбор ветки загрузки, но не успешные calibration writes: есть ранние выходы, а функция загрузки калибровки возвращает `void`. [Linux `tas2781-fmwlib.c`, `tasdev_load_calibrated_data()`](https://github.com/torvalds/linux/blob/master/sound/soc/codecs/tas2781-fmwlib.c).

Штатный script читает timeout при переходе состояния; уже заведённый timer сам от изменения политики не пересоздаётся. [WP `suspend-node.lua`](https://github.com/PipeWire/wireplumber/blob/master/src/scripts/node/suspend-node.lua).

## CHANGED MY MIND

Статический `Force Firmware Load` — лучший первый эксперимент, но **не безусловная гарантия исправного звука при любых ошибках**. Он гарантирует нужную последовательность попыток загрузки до playback; валидность данных и успешность I2C надо подтвердить.

Убирать одновременно keep-open и forced-runtime-PM rule не стоит. Сначала проверить reopen с force flag, затем отдельным экспериментом разрешить runtime PM. Иначе при регрессии хуй поймёшь, какой переход её вызвал.

## UNRESOLVED

- Не декодирован конкретный Lenovo RCA shutdown/power-up block: какой write уничтожает или заменяет калибровку, пока не установлен.
- Не измерены реальные amp rails, power mode и потери преобразователей.

## FINAL ANSWER

**Практический вариант: вооружить `Speaker Force Firmware Load` до OPEN, оставить его включённым и вернуть обычный idle suspend. Отдельный watcher начала звука — лишняя ебля с гонкой.** Ничего на машине не менял, звук не запускал, sudo не использовал.

### 1. Куда уходят 0,65 Вт

По TAS2781 при цифровой тишине, IV sense enabled, предполагаемых AVDD=1,8 V, PVDDL=3,8 V и PVDDH=8–12 V:

| Режим | Оценка для двух amps |
|---|---:|
| PWR_MODE1 | ≈0,073 W |
| PWR_MODE0 | ≈0,109–0,127 W |
| PWR_MODE2 | ≈0,104–0,128 W |
| Software shutdown, clocks stopped | ≈40 µW |

Это экстраполяция типовых токов, измеренных TI преимущественно при 18 V; батарейные потери регуляторов сюда не входят. Hardware shutdown тоже имеет утечки: буквальный ноль требует отключённых rails. [TI TAS2781, §6.5, страницы 9–10](https://www.ti.com/lit/ds/symlink/tas2781.pdf).

**Вероятнее всего, основная часть 0,65 W — SOF/HDA/codec и SoC/graph activity**, но точное распределение не измерено. Открытый PCM не доказывает непрерывную максимальную активность DSP: SOF имеет opportunistic D0I3, включая проверку допустимости streaming. [Linux `hda-dsp.c`, `hda_dsp_d0i3_streaming_applicable()`](https://github.com/torvalds/linux/blob/master/sound/soc/sof/intel/hda-dsp.c).

Read-only сравнение естественно возникающих closed/open состояний:

- Battery `power_now` либо energy delta вместе с **package RAPL energy delta**: отделяет значительную часть SoC от внешних rails.
- Package C8/C10 residency, если доступен уже разрешённый `turbostat`; проверять LPIT counter на обоих интервалах.
- PCM `status`, audio PCI/I2C `runtime_status`, `pw-top`, interrupt/context-switch deltas: отличает просто открытый PCM от работающего графа.
- Стабильные brightness, workload, температура; длинные интервалы, несколько повторов.

Без rail measurement или контролируемого изменения amp state **точно разделить amps, codec и regulator losses нельзя**. `runtime_status=active` сам по себе не ваттметр.

### 2. Calibration и порядок OPEN

В `tasdevice_select_tuningprm_cfg()` запись калибровки находится внутри ветки изменения **per-device** `cur_conf`. `force_fwload_status` заставляет повторно загрузить программу и инвалидировать этот кеш. Затем идут config/calibration и PRE_POWER_UP block. Поэтому штатный минимальный механизм — **force flag до следующего OPEN**, при исправных firmware/calibration/I2C. После OPEN этот setter текущий звук не исправляет. [Linux `tas2781-fmwlib.c`, `tasdevice_select_tuningprm_cfg()`, `tasdevice_tuning_switch()`](https://github.com/torvalds/linux/blob/master/sound/soc/codecs/tas2781-fmwlib.c).

Исторический [`bec7760a6c5fa59593dac264fa0c628e46815986`](https://github.com/torvalds/linux/commit/bec7760a6c5fa59593dac264fa0c628e46815986) убрал инвалидирование `cur_*` в runtime suspend, исходя из сохранения регистров software shutdown. Это объясняет намерение кеширования, **не доказывает**, что именно этот commit вызвал Lenovo firmware-specific потерю.

### 3. Выключить amps при живом PCM

Железо имеет software shutdown с сохранением регистров; mute оставляет Class-D switching. [TI, operating modes](https://www.ti.com/lit/ds/symlink/tas2781.pdf).

Текущий HDA интерфейс отдельного amp shutdown control не предоставляет. Playback pin switches — не доказанный amp-power API. OPEN держит runtime-PM reference до CLOSE; `power/control=auto` не обходит его. Runtime resume вызывает `tasdevice_prmg_load()` без безусловной записи калибровки. CLOSE уже запускает shutdown block даже при forced `power/control=on`. [Linux `tas2781_hda_i2c.c`, playback hook и runtime callbacks](https://github.com/torvalds/linux/blob/master/sound/hda/codecs/side-codecs/tas2781_hda_i2c.c).

Добавлять driver-owned shutdown возможно, но это сохранит расходы открытого SOF/HDA пути.

### 4. Минимальная предлагаемая логика

**Эскиз, не выполненные команды:**

```text
ALSA card/control available, after ALSA state restore:
    identify the sof-hda-dsp card
    set Speaker Force Firmware Load = on
    read back; require success
    only then expose the speaker playback path

Playback:
    kernel OPEN reloads program/config/calibration synchronously

Idle:
    WirePlumber idle timer expires
    Suspend → PCM CLOSE → amp shutdown
    SOF/HDA suspend when other streams permit
```

Единственная ALSA настройка:

```bash
amixer -c "$card" cset name='Speaker Force Firmware Load' on
```

В существующем speaker match заменить timeout `0` на `3`–`5` секунд. Для строгого event-driven startup ждать ALSA control ADD/card readiness, а не крутить sleep/retry loop. Обычная service ordering только относительно WirePlumber недостаточна при асинхронном появлении control.

| Вариант | Вывод |
|---|---|
| WP Lua на `running` | Поздно: OPEN уже произошёл |
| WP ordered startup hook | Подходит для arming до доступности speaker path |
| `pactl subscribe` | Поздно; raw PipeWire links могут быть невидимы |
| `pw-mon` | Полнее, но остаются OPEN/reconnect races |
| Timeout по питанию | Полезная политика, калибровку не чинит |
| Persistent flag + штатный suspend | Минимальный рабочий кандидат |

WP 0.5 поддерживает ordered synchronous/asynchronous hooks. [Events & Hooks](https://pipewire.pages.freedesktop.org/wireplumber/scripting/lua_api/lua_events_api.html).

Штатная политика реагирует на **idle**, а не на нулевые samples. Если `yoga_dolby` держит hardware node running бесконечно, timeout не сработает: сначала требуется исправить жизненный цикл filter-chain. [WP suspend script](https://github.com/PipeWire/wireplumber/blob/master/src/scripts/node/suspend-node.lua).

### 5. Риски и проверка

- Full reload увеличивает OPEN latency; «первые 100 ms точно хорошие» пока обещать нельзя.
- Последовательность внутри OPEN устраняет watcher race, но не гарантирует доставку каждого короткого уведомления клиентом.
- Pop/click измерять всей цепочкой: паспортный ramp отдельного чипа недостаточен.
- `alsactl restore` может перезаписать force flag; arming после restore, повторять после reprobe. Не сохранять промежуточный `Config Id=1`.
- Другие playback/capture streams могут удерживать DSP.

Будущая авторизованная проверка: dynamic debug показывает OPEN/CLOSE/reload/skip; затем tracing либо instrumentation подтверждает **пять успешных calibration bulk writes для каждого amp**, включая register addresses и return codes. Отсутствия error logs мало. После этого — одинаковая акустическая АЧХ после boot/reopen, измерение transient/start latency, idle power и повторения reboot, suspend/resume, WP restart. Sink-monitor проверяет цифровой EQ, усилительную калибровку он не видит.

Окончательный driver fix должен восстанавливать подтверждённо потерянное состояние перед power-up и учитывать ошибки загрузки. Просто инвалидировать config на CLOSE — разумный кандидат, но без разбора firmware blocks это ещё гипотеза.

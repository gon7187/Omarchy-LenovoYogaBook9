# Yoga Book 9 speaker amps: power logic design (agent a1, round 1)

Recommendation: drop the keep-open workaround, let the PCM close when idle, and set `Speaker Force Firmware Load` once per boot so every open reloads the calibration. No watcher is needed.

Nothing was changed on the machine. Most shell commands were denied in this session, so I could not run `amixer contents`, `wpctl status` or read the kernel log. Live facts below come from sysfs/procfs reads only; the design itself is untested.

## 1. Where the 0.65 W goes

**The amps are the small part: about 0.1–0.15 W for both.** TAS2781 datasheet (SLOSE86B, §6.5 "Typical Current Consumption", p. 9–10; test condition PVDDH 18 V, PVDDL 3.8 V, AVDD 1.8 V):

| Mode | AVDD (1.8 V) | PVDDL (3.8 V) | PVDDH | Per amp |
|---|---|---|---|---|
| Idle, PWR_MODE1 | 15.5 mA | 2.2 mA | 0.04 mA | ≈ 37 mW |
| Idle, PWR_MODE0 | 15.5 mA | 2.1 mA | 2.3 mA at 18 V, ≈ 1.6 mA at 10 V (Fig. 6-27) | ≈ 52 mW |
| Noise gate | 8.2 mA | 0.13 mA | 0.012 mA | ≈ 15 mW |
| Software shutdown | 10 µA | 0.5 µA | 0.05 µA | ≈ 20 µW |

Two amps idle is 75–105 mW, or roughly 0.09–0.15 W at the battery after regulator losses. I don't know which power mode Lenovo's tuning selects.

**The remaining ≥ 0.5 W is on the SoC side**: SOF DSP and HDA controller held in D0, the ALC287 powered, and possibly a running PipeWire graph. Two live observations matter here:

- **The PCM was `RUNNING`, not just open.** `/proc/asound/card0/pcm0p/sub0/status` showed `state: RUNNING` with about 32 minutes of continuous run time (hw_ptr 91035072 at 48 kHz). I could not check whether something was actually playing. If the sink stays running when idle (for example because `yoga_dolby` keeps it driven), the graph wakes every 1024-frame period (~47 times a second) and that is part of the 0.65 W.
- **Package C10 is not what is being lost.** `/sys/devices/system/cpu/cpuidle/low_power_idle_cpu_residency_us` read `0` after more than two hours of uptime. The cost is in shallower package or core C-states and device D0 power.

**Measurement that splits them** (battery, fixed brightness, 2–3 minutes per state, average `power_now` from `/sys/class/power_supply/BAT*/`):

| State | How to get there | What is on |
|---|---|---|
| S0 | Fresh boot, no sound yet, udev rule active | Amps active, DSP and codec suspended, PCM closed |
| S1 | After a PCM close | Amps shut down, everything suspended |
| S2 | PCM open but sink paused | Amps, DSP and codec on, no graph wakeups |
| S3 | PCM running silence | S2 plus graph wakeups |

- S0 − S1 = amps alone; S2 − S0 = DSP, link and codec; S3 − S2 = PipeWire wakeups.
- S0 exists because the udev rule blocks `tas2781_runtime_suspend`, the only path that undoes the load-time amp power-up (per the driver's own comment there).
- If the 8.93 W baseline was taken in S0, the whole 0.65 W is SoC-side.
- Cross-check each state with `power/runtime_status` of `0000:00:1f.3` and `i2c-TIAS2781:00`, and the PCM `status` file.

## 2. The calibration bug: still present, no upstream fix

I read both `v7.2` and current master. The commit histories of `sound/soc/codecs/tas2781-fmwlib.c` and `sound/hda/codecs/side-codecs/tas2781_hda_i2c.c` through August 2026 (latest f6635d6, 431c156, b601633) contain no fix.

The mechanism, in v7.2:

- **Open:** `tas2781_hda_playback_hook` calls `tasdevice_tuning_switch(priv, 0)`, which calls `tasdevice_select_tuningprm_cfg(cur_prog, cur_conf, profile)` and then the RCA power-up block.
- **Calibration write:** `tasdev_load_calibrated_data()` is called only inside the "config needs loading" branch, when `tasdevice[i].cur_conf != cfg_no`. Otherwise it logs `Unneeded loading dsp conf %d` and writes nothing.
- **First open after boot works** because `tasdevice_dspfw_init` loads the program, which leaves the per-device `cur_conf` at −1. Every later open skips.
- **History:** commit bec7760 ("do not reset cur_* values in runtime_suspend", March 2024) removed the old invalidation, on the premise that the amp keeps its registers in software shutdown.

I could not confirm that the amp really loses the calibration registers across the shutdown/power-up blocks; that needs root register access. The symptom and the code path are consistent with it.

**The documented toggle does not do what the README says.** `tasdevice_config_put` only stores `priv->cur_conf`; it writes no hardware. So `cset numid=5 1; cset numid=5 0` with no PCM open in between is a no-op by the code. If it appeared to work, an open must have happened between the two writes. Check this with dynamic debug before relying on it.

**Minimal action that guarantees calibration: `Speaker Force Firmware Load` = on (numid=3).**

- With the flag set, every open forces `cur_conf = -1`, reloads program and config, and writes the calibration.
- It must be set **before** the open. All of these controls only store a value that the open hook consumes; nothing written after open reaches the amp until the next close/open or a system resume.
- Cost: a linux-sound report from 2026-06-07 (Yoga Pro 9 16IMH9, same driver and control) describes this as working, with a 2–3 s playback delay after idle.

## 3. Powering the amps down while the PCM stays open

There is no supported way, and it would recover at most ~0.1 W.

- **Kcontrols:** none power the amp. The amp driver's own controls are the analog volume, the force-load flag and the stored profile/program/config ids; numid 7 and 9 are codec pin switches.
- **Runtime PM:** the driver holds a runtime-PM reference from open to close, so the amp cannot autosuspend under an open PCM.
- **Runtime resume does not reload calibration.** `tas2781_runtime_resume` only calls `tasdevice_prmg_load(cur_prog)`, which is a no-op when the program is unchanged. Only `tas2781_system_resume` resets `cur_*` to −1 and reloads everything.
- **The udev rule is not helping.** After a close the amps are already shut down and `runtime_suspend` does nothing. The rule's only effect is to keep the amps active from boot until the first close. I could not tell whether ACPI D3 cuts amp power on this machine.
- **Noise gate** (datasheet §8.4.2.8) drops the amp to ~15 mW on silence, but it is set by the firmware blob and has no control exposed.

## 4. Proposed logic

**Best option (d): a static kernel flag plus normal WirePlumber suspend.**

1. Once per boot, set `Speaker Force Firmware Load` on. The control is created asynchronously after firmware load, so retry until it exists:
   ```bash
   # bin/yoga-amp-arm, started from a user unit after wireplumber
   for _ in $(seq 50); do
     amixer -c0 -q cset name='Speaker Force Firmware Load' on 2>/dev/null && exit 0
     sleep 0.2
   done; exit 1
   ```
2. Remove `52-yoga-speakers-keep-open.conf`, or set the timeout to 10–30 s so short gaps between sounds do not each cost a 2–3 s reload.
3. Remove `90-yoga-tas2781-no-runtime-pm.rules`, so the amps are shut down 3 s after boot instead of idling until the first close.

It is race-free because the reload runs synchronously inside the open hook, before any audio is triggered.

**Why not the others:**

- **(a) WirePlumber Lua hook on `node-state-changed`:** it fires after the device is already open, which is too late. The only useful variant is "arm on suspended", which is the same as the static flag with more moving parts.
- **(b) `pactl subscribe` / `pw-mon` watcher:** same after-open race, plus an extra process.
- **(c) suspend-timeout per power source:** only decides when to close, not how to recalibrate. WirePlumber rules are static, so switching on AC/battery means rewriting a fragment and restarting WirePlumber (an audible glitch). Worth adding only if the reload delay is annoying on AC.
- **Real fix:** a kernel patch that sets `tasdevice[i].cur_conf = -1` on close, so the next open reloads config and calibration without the program (far cheaper than 2–3 s). Worth sending to linux-sound, referencing the Yoga Pro 9 thread.

**Failure modes:**

- **Start delay:** 2–3 s on the first sound after idle. Short notification sounds arrive late; the open blocks rather than dropping audio, but I have not tested that.
- **Pop/click:** datasheet lists 0.8 mV click-and-pop into and out of shutdown, and turn-on in 1.1–6.7 ms, so the power transition itself should be quiet. A pop during the program reload is possible and untested.
- **Reload failure:** if an I2C block write fails mid-reload, that open plays untuned. Recent upstream commits (513480d, f6635d6) touch exactly this retry path. Watch the kernel log for `process_block` errors.
- **Flag persistence:** it resets to off on boot or module reload, hence the arming unit. `alsactl` may also save and restore it, which is harmless.
- **Race at login:** if the first open beats the arming script, that open is still calibrated (per-device `cur_conf` is −1 after boot).

**Verification without ears:**

1. Enable dynamic debug (needs root, read-only for audio): `echo 'module snd_soc_tas2781_fmwlib +p; module snd_hda_scodec_tas2781_i2c +p' > /sys/kernel/debug/dynamic_debug/control`.
2. Reproduce the bug with the flag off: a reopen logs `action = 0` followed by `Unneeded loading dsp conf 0`.
3. With the flag on: a reopen must **not** log "Unneeded", and must show no `r0_reg bulk_wr err`. Take the reload duration from the journal timestamps between `action = 0` and the next line.
4. Test the README toggle under debug to confirm it is a no-op without an open.
5. Confirm the idle state: PCM `status` reads `closed`, `0000:00:1f.3` is `suspended`, and battery power returns to ~8.9 W.
6. Objective audio check: the existing sink-monitor EQ measurement is digital and will not show it. Record a sweep with the internal mic after boot and after a reopen, and compare the 100–300 Hz level.

**Главная находка: `Speaker Config Id: 1 → 0` не гарантирует перезагрузку калибровки. На установленном 7.2.5 setter только меняет переменную. Надёжнее вооружить `Speaker Force Firmware Load` до OPEN и позволить PCM закрываться. Watcher после начала звука уже опоздал.**

Ничего не менял, звук не запускал, sudo не использовал. Проверил локальные файлы и машинный код установленных модулей через анонимный `memfd`, без создания файлов.

### 1. Куда уходят 0,65 Вт

**Списывать всё на усилители — наебалово.** TI приводит следующие типичные токи цифровой тишины при 48 kHz, IV sense enabled:

| Режим | PVDDH | PVDDL | AVDD |
|---|---:|---:|---:|
| PWR_MODE0 | 2,3 mA | 2,1 mA | 15,5 mA |
| PWR_MODE1 | 0,04 mA | 2,2 mA | 15,5 mA |
| PWR_MODE2 | 3 mA | внутренний LDO | 15,5 mA |

При **предполагаемых** PVDDH=8–12 V, PVDDL=3,8 V, AVDD=1,8 V это даёт примерно:

- MODE0: **0,109–0,127 Вт на пару**;
- MODE1: **0,073 Вт на пару**;
- MODE2: **0,104–0,128 Вт на пару**.

Это оценка, экстраполированная из типовых значений при PVDDH=18 V; реальные rail voltages, режим, прошивка и потери преобразователя неизвестны. Noise gate уменьшает потребление ещё сильнее. Software shutdown сохраняет регистры; с остановленными clocks потребление пары около **40 µW**, не буквальный ноль. [TI TAS2781 datasheet, §6.5, pp. 9–10; §8.5](https://www.ti.com/lit/ds/symlink/tas2781.pdf).

**Вероятнее всего, 0,65 Вт — смесь**, с существенной долей SOF/HDA/SoC и возможных graph wakeups. Сам факт открытого PCM не доказывает отсутствие package C10. SOF поддерживает opportunistic D0I3 при подходящих потоках; полноценный suspend выключает HDA links и DSP. [Linux `sound/soc/sof/intel/hda-dsp.c`: `hda_dsp_d0i3_streaming_applicable()`, `hda_suspend()`](https://github.com/torvalds/linux/blob/master/sound/soc/sof/intel/hda-dsp.c).

**Как разделить read-only измерениями**, используя уже существующие/естественно возникающие состояния closed и held-open:

1. Одновременно записывать battery power и package RAPL energy delta. Рост package power объяснит долю SoC; остаток вне package включает amps, codec и преобразователи.
2. Сравнить package C8/C10 residency через `turbostat`, если доступ разрешён заранее. CPU core C-state counters не заменяют package residency.
3. `pw-top`, `/proc/interrupts`, счётчики context switches/process CPU для PipeWire/WirePlumber: есть ли периодическая обработка графа при тишине?
4. Снять `runtime_status`/`runtime_active_time` для `0000:00:1f.3`, HDA codec и amp I2C device; проверить PCM status.

**Предел метода:** RAPL + residency отделяют значительную долю SoC, но не позволяют точно развести amps/codec/rail losses. Для этого нужен ток rail либо контролируемый A/B с отключением amps — последнее уже выходит за read-only.

Здесь прочитано: PCM `RUNNING`, amp `active`, `power/control=on`, PCI audio `active`. RAPL `energy_uj` отказал в доступе; PipeWire socket в sandbox также недоступен. Поэтому доли ватт я не измерил.

### 2. Что реально происходит с калибровкой

В newest mainline сохраняется проблемная последовательность:

- OPEN: runtime PM reference → `tasdevice_tuning_switch(..., 0, false)`;
- CLOSE: shutdown block → release runtime PM reference;
- конфигурация и calibration writes пропускаются при совпадении cached configuration;
- runtime resume вызывает `tasdevice_prmg_load(cur_prog)`, без безусловного восстановления калибровки.

Это совпадает с проверенными вызовами установленного `7.2.5-3-omarchy` модуля. [Linux `tas2781_hda_i2c.c`: `tas2781_hda_playback_hook()`, `tas2781_runtime_resume()`](https://github.com/torvalds/linux/blob/master/sound/hda/codecs/side-codecs/tas2781_hda_i2c.c).

**Исходники подтверждают отсутствие повторных writes; сами по себе они не доказывают, какой конкретно firmware block уничтожает значения.** Поэтому факт «после CLOSE калибровка потеряна» пока опирается на машинное наблюдение из README, а не на декодированный RCA shutdown block.

**Ключевая поправка:** `tasdevice_config_put()` обновляет только `tas_priv->cur_conf`. Быстрый `1 → 0` при открытом PCM ничего не загружает; такой же toggle до OPEN возвращает желаемую конфигурацию к прежней и тоже не заставляет per-device cache измениться. Это подтверждено disassembly именно установленного модуля. [Linux `tas2781_hda.c`: `tasdevice_config_put()`](https://github.com/torvalds/linux/blob/master/sound/hda/codecs/side-codecs/tas2781_hda.c).

**Минимальный штатный userspace механизм — установить `Speaker Force Firmware Load=on` ДО следующего OPEN.** Это persistent flag, а не немедленная команда загрузки. На OPEN он заставляет загрузить program, инвалидирует per-device config cache, затем загрузить configuration и вызвать `tasdev_load_calibrated_data()` для активных amps. Установка после OPEN действует лишь на следующий OPEN. Оставить flag включённым проще и исключает гонку повторного вооружения. Условия: валидные calibration data, правильный профиль/конфигурация и успешные I2C writes. [Linux `tas2781-fmwlib.c`: `tasdevice_select_tuningprm_cfg()`, `tasdevice_tuning_switch()`](https://github.com/torvalds/linux/blob/master/sound/soc/codecs/tas2781-fmwlib.c).

**Подтверждённого upstream commit, исправляющего именно CLOSE/OPEN caching bug, не нашёл.** Не путать:

- [`b601633`](https://github.com/torvalds/linux/commit/b601633) исправляет invalid calibration handling для TAS2563;
- [`b7e26c8bdae70832d7c4b31ec2995b1812a60169`](https://github.com/torvalds/linux/commit/b7e26c8bdae70832d7c4b31ec2995b1812a60169) отключает UEFI calibration на ASUS ROG Xbox Ally X.

Оба не являются исправлением этой Yoga CLOSE/OPEN проблемы.

### 3. Можно ли выключать только amps, сохранив PCM

**Железо умеет; текущий HDA интерфейс этого нормально не предоставляет.**

- TAS2781 software shutdown сохраняет register state.
- Mute не эквивалентен shutdown: Class-D продолжает переключаться.
- Hardware shutdown теряет register state.
- HDA playback switches на pins 0x17/0x14 нельзя считать amp power controls.
- `Speaker Analog Volume`, Profile/Program/Config и Force Firmware Load не являются отдельным idle-power control.
- `power/control=auto` лишь разрешает runtime PM. OPEN держит reference до CLOSE, поэтому idle при открытом PCM не даёт автоматически suspend усилителей.

Ни «mute sink», ни разрешение runtime PM не обеспечивают требуемого выключения при живом PCM. Driver-owned software-shutdown control можно добавить, но он сохранит расходы SOF/HDA. Не стоит обходить драйвер raw I2C writes: потеряется согласованность его state/cache.

### 4. Конкретная логика

**Лучший минимальный вариант сейчас: постоянный Force Firmware Load + обычный idle suspend.** Event-driven power sequencing уже находится в ядре; отдельный watcher здесь — лишняя ебля.

Схема предлагаемой реализации, **не выполненная**:

```text
Before enabling/restoring the speaker playback path:
    resolve ALSA card by identity, not fixed card number
    validate calibration and expected profile/program/config
    set "Speaker Force Firmware Load" = on
    read back and require success
    enable normal speaker path

On playback:
    kernel OPEN performs firmware/config/calibration sequence
    audio starts after OPEN completes

On idle:
    WirePlumber sends Suspend after 2–5 seconds
    PCM CLOSE runs amp shutdown
    SOF/HDA may runtime-suspend when no other user remains
```

Предлагаемые значения WP:

```ini
session.suspend-timeout-seconds = 3
```

**Не менять runtime PM workaround одновременно с этим первым экспериментом.** PCM CLOSE уже вызывает amp shutdown при `power/control=on`; сначала подтвердить исправность reopen. Затем отдельно проверить возможность убрать forced-on rule и отсутствие потери состояния при runtime suspend/resume.

WirePlumber уже использует `node-state-changed`, отменяет idle timer при смене состояния и отправляет `Suspend`; значение `0` отключает timer. [WP `src/scripts/node/suspend-node.lua`](https://github.com/PipeWire/wireplumber/blob/master/src/scripts/node/suspend-node.lua).

| Вариант | Оценка |
|---|---|
| Lua hook на `running` | Хорош для наблюдения, поздний для гарантии первого звука |
| `pactl subscribe` | Поздний, Pulse-only; raw PipeWire/filter links могут пройти мимо |
| `pw-mon` watcher | Полнее, но parsing/reconnect/object-ID races; тоже поздний |
| Timeout по питанию | Полезная политика: батарея 3 s, AC 0/больше; калибровку не исправляет |
| Persistent force flag + штатный suspend | Минимум кода, calibration sequence внутри OPEN |
| Driver fix | Лучшее окончательное решение после подтверждения реальных потерянных registers |

Если нужен startup hook, он должен **задерживать доступность speaker path до успешной установки flag**, а не реагировать на `running`. WP 0.5 предоставляет ordered `AsyncEventHook` для ожидающих операций; один hook не может гарантировать порядок относительно стороннего direct ALSA client. [WirePlumber Events & Hooks](https://pipewire.pages.freedesktop.org/wireplumber/scripting/lua_api/lua_events_api.html).

### Риски и проверка

- **Startup race:** восстановление `alsactl` может перезаписать force flag; устанавливать его после restore и до разрешения speaker path. Не сохранять промежуточный Config Id=1.
- **Время старта:** full firmware reload увеличит OPEN latency. Гарантировать «100 ms» без трассы нельзя.
- **Первый звук:** watcher после `running` допускает некалиброванный фрагмент. Последовательность внутри OPEN устраняет именно эту userspace гонку.
- **Pop/click:** configuration/program reload и firmware blocks могут давать артефакты. Нужны измерения; паспортный ramp не гарантирует результат всей laptop цепочки.
- **«Нет звука» ≠ silence samples:** поток, который бесконечно передаёт нули, остаётся running и не suspend. Для отключения такого потока нужен отдельный silence detector/hardware noise gate; обычная session policy понимает отсутствие активного потока.
- **DSP off:** другие playback/capture streams могут удерживать SOF независимо от speakers.

План последующей авторизованной проверки:

1. Включить dynamic debug для `tas2781_hda_i2c.c` и `tas2781-fmwlib.c`; фиксировать OPEN/CLOSE/runtime transitions и сообщения reload/skip.
2. **Отсутствие `"Unneeded loading dsp conf"` не является доказательством calibration writes.** В `tasdev_load_calibrated_data()` нет безусловного success log. Нужны function tracing/kprobe либо driver instrumentation на пяти успешных bulk writes обоих amps; статическая функция может быть inlined — установленный модуль именно так и выглядит.
3. Проверить register values через согласованный driver/debug интерфейс, если он доступен; отдельно проверить акустическую АЧХ внешним микрофоном. Sink monitor показывает цифровой сигнал до усилителей и калибровку не доказывает.
4. Повторить короткую паузу, паузу длиннее timeout, browser restart, suspend/resume, WirePlumber restart и reboot.
5. Измерить cold-start delay и transient waveform; подтвердить shutdown при idle и восстановление всех calibration writes на каждом reopen.
6. Затем повторить battery/RAPL/C-state сравнение с отключёнными диагностическими трассами.

**Итого по доказательствам:** caching path остался; runtime resume не лечит его; documented Config toggle оказался бесполезным без intervening load. Force flag до OPEN — реальный штатный кандидат на снятие keep-open workaround, но принятие решения требует доказать успешные writes и звук после полного firmware power-up sequence.
